Ревью выявило два блокирующих дефекта отбора и несколько существенных проблем с идентичностью входов, памятью и отчётом. Успешный CPU smoke с десятью статусами `success` не подтверждает корректность выбранных признаков.

1. **P0 — файлы рейтингов содержат неверные длины списков классов.** В [attribution.py](/home/ustyantsev/workspace/KKT/kkt_mlp_classifier/kkt_clf/attribution.py:387) в `counts[ci]` записывается число строк класса, а не число его положительных признаков `len(ranked)`. При этом `_RankStream` использует эти значения как длины и смещения списков ([selection.py](/home/ustyantsev/workspace/KKT/kkt_mlp_classifier/kkt_clf/selection.py:403)). Например, если у класса две строки и десять положительных кандидатов, следующий класс начнёт чтение с третьего кандидата первого класса. Если кандидатов меньше числа строк, чтение может завершиться ошибкой об обрыве файла. Даже успешный run может приписать признаки и оценки неверным классам и нарушить round-robin. **D05, D06 и достоверность результатов G×I не выполнены.**

2. **P1 — пустые векторы исключены из знаменателя и покрытия классов, вопреки D05.** [attribution.py](/home/ustyantsev/workspace/KKT/kkt_mlp_classifier/kkt_clf/attribution.py:321) удаляет все `att.empty` до расчёта `N_c`; при этом margin и предсказание для них уже вычислены. Для класса с одной непустой строкой с вкладом 2 и одной пустой строкой контрактная оценка равна 1, а реализация выдаёт 2. Класс, состоящий только из пустых векторов, исчезает из рейтингов и диагностики классов. Политика в manifest честно описывает это поведение, но не устраняет противоречие требованию считать все атрибутированные строки.

3. **P1 — проверка загружаемого checkpoint не подтверждает ни full TF-IDF, ни фактический train split.** [verify_attribution_checkpoint](/home/ustyantsev/workspace/KKT/kkt_mlp_classifier/kkt_clf/attribution.py:652) сравнивает лишь размерность, hash label maps, конфигурацию данных и seed. Два векторизатора с одинаковой размерностью, но разным порядком словаря или IDF пройдут проверку; изменение содержимого parquet по тому же пути также не будет обнаружено. Воспроизведение: обучить checkpoint, затем подменить full TF-IDF на другой той же размерности либо изменить данные по прежнему пути и загрузить checkpoint. Атрибуция будет вычислена по несовместимым признакам или другому train, несмотря на сообщение об успешной проверке. Нужны проверяемые fingerprints полного контракта признаков и фактических split/данных, сохранённые при обучении checkpoint.

4. **P1 — построение рейтингов может занимать память порядка числа пар «класс–признак».** В [attribution.py](/home/ustyantsev/workspace/KKT/kkt_mlp_classifier/kkt_clf/attribution.py:382) массивы всех положительных кандидатов всех классов накапливаются в `idx_parts` и `score_parts`, затем дополнительно копируются через `np.concatenate`. При 1000 классах и 400 тыс. положительных признаков на класс только индексы и scores занимают около 6,4 ГБ до дополнительных копий. Кроме того, сохраняется CSR всех вкладов и создаются его копии. Это противоречит заявленной ограниченной последовательной агрегации D06; отсутствие *плотной* `C×F` матрицы само по себе не ограничивает этот худший случай.

5. **P1 — отчёт допускает дельты для несопоставимых запусков.** [_comparable_identity](/home/ustyantsev/workspace/KKT/kkt_mlp_classifier/kkt_clf/experiment.py:1523) проверяет только hash validation и label maps. Если подставить сохранённый `run_result.json` другого эксперимента с теми же validation и maps, но иным train, full TF-IDF, seed или настройками модели, `build_report` рассчитает дельты и объединит результаты. Для S04 этого недостаточно: требуются идентификаторы фактического train, признаков, настроек модели и протокола. Аналогично графики строятся по всем успешным runs без проверки этой полной сопоставимости ([experiment.py](/home/ustyantsev/workspace/KKT/kkt_mlp_classifier/kkt_clf/experiment.py:1945)).

6. **P2 — GPU-путь атрибуции не переносит индексы и offsets на устройство.** В [attribution.py](/home/ustyantsev/workspace/KKT/kkt_mlp_classifier/kkt_clf/attribution.py:233) `weights` создаются на `device`, но `batch.indices` и `batch.offsets` остаются на CPU. Первый проход переносит весь batch через `.to(device)`, второй — нет. На CUDA это приводит к ошибке смешанных устройств. CPU smoke эту проблему не покрывает; GPU в DoD допускается оставить непроверенным, но код конфигурационно выбирает устройство и должен корректно сообщать об ограничении или работать.

7. **P2 — обязательные данные и сравнение ресурсов в отчёте неполны.** В manifest попадает лишь общая `summary`, без числа использованных строк по каждой L3; оно находится во внешнем `report.json` ([experiment.py](/home/ustyantsev/workspace/KKT/kkt_mlp_classifier/kkt_clf/experiment.py:906)). Раздел «качество ↔ ресурсы» содержит таблицу с временем финальной MLP, но требуемого графика и рассчитанной суммарной стоимости сценария с однократным учётом общих затрат нет ([experiment.py](/home/ustyantsev/workspace/KKT/kkt_mlp_classifier/kkt_clf/experiment.py:1994)). Текст предлагает читателю прибавить общие этапы вручную. Это оставляет D10 частично невыполненным.
