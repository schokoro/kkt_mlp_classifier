# Спека: классификатор позиций чеков, итерация 1 (baseline)

Статус: черновик на ревью. Исполнитель: облачная сессия Claude Code.

Метки статуса утверждений: **[Ф]** факт, **[Р]** согласованное решение, **[Г]** рабочая гипотеза (можно менять, если есть основания, с записью в `DECISION_LOG.md`, см. §8).

---

## 1. Value

Первая итерация классификатора наименований позиций из реальных кассовых чеков по трёхуровневой таксономии (L1 → L2 → L3). Итерация нужна для трёх вещей:

- получить воспроизводимый **baseline**, от которого будут мериться следующие итерации;
- понять, куда развивать пайплайн дальше: какие звенья (предобработка, признаки, модель, отказ) — узкие места и что дорабатывать в первую очередь;
- иметь работающий сквозной пайплайн «данные → модель → метрики → инференс», который можно показать.

Задача итерации — работающий пайплайн с честными метриками. Production-качество не требуется. Метрики максимизируются в разумных пределах без подбора гиперпараметров.

## 2. Контекст и ограничения

- **[Ф]** Вход модели — только строка наименования `name`. Никакие другие признаки (касса, продавец, внешние описания) не используются.
- **[Ф]** Данные — parquet, уже отфильтрованы. Колонки: `name`, `L1`, `L2`, `L3`. Путь к файлу задаётся в конфиг-ячейке ноутбука.
- **[Ф]** Классы «другое» и «не классифицируется» удалены на этапе фильтрации, в данных их нет.
- **[Ф]** Таксономия восстанавливается из файла данных. Пути уникальны: каждая L3 имеет ровно одного родителя L2, каждая L2 ровно одного родителя L1. Покрыты не все категории полной таксономии. Работаем с тем, что есть в файле.
- **[Ф]** Рабочий 6-миллионный датасет исполнителю недоступен.
- **[Ф]** В репозитории есть `data/ods_labels.csv`: открытый размеченный набор в том же формате (колонки `L1,L2,L3,name`, ~18 тыс. строк, предобработка применена). Таксономия покрыта не полностью, для разработки это не важно. Это основной источник данных для разработки, фикстур и сквозных прогонов. Файл не изменяется.
- **[Р]** ODS нужен только для разработки пайплайна. Дефолты конфига (`max_features`, размеры слоёв, batch size, число эпох и т. п.) рассчитываются на обучение в контуре на ~6 млн строк, а не подгоняются под ODS. Для прогонов на ODS допускается отдельный лёгкий пресет. Отсечение части классов по `min_count` ожидается и на обоих наборах и проблемой не считается.
- **[Ф]** Целевая среда запуска: **Python 3.12**, Jupyter, 24 ГБ RAM, 8 CPU, один GPU (H100 или A100).
- **[Ф]** В целевую среду переносится **только код**. Пакеты ставятся через `pip` из внутреннего зеркала. `uv`, `conda` и marimo недоступны. Импорт предобученных моделей ограничен, поэтому никаких скачиваемых весов.
- **[Р]** PySpark не используется. Чтение parquet через `pyarrow`/`pandas`.
- **[Р]** Код должен работать и на CPU, без GPU: устройство выбирается автоматически. Это нужно для тестов в облачной сессии.
- **[Ф]** Объём файла в этой итерации — около 6 млн строк. Пайплайн должен укладываться в 24 ГБ RAM на этом объёме. Параметр `max_rows` остаётся для быстрых прогонов.
- **[Ф]** Входной датасет стерильный: дубликатов нет, предобработка уже применена. Последняя операция предобработки — `lower()`, после неё удалены пустые строки. Проверки в §4.1 нужны только как страховка и ничего не исправляют молча.

## 3. User stories

1. Как пользователь, я указываю путь к parquet в конфиг-ячейке, запускаю обучающий ноутбук целиком (Run All) и получаю обученную модель, сохранённую на диск, и отчёт с метриками.
2. Как пользователь, я задаю в конфиг-ячейке архитектуру MLP (число и размерность скрытых слоёв, дропауты), параметры векторизации и обучения, не трогая код модуля.
3. Как пользователь, я вижу `sklearn.metrics.classification_report` для L1, L2 и L3 на test, с отказом и без отказа, плюс покрытие (долю неотказанных).
4. Как пользователь, я открываю отдельный ноутбук инференса, указываю путь к артефакту модели и к parquet с колонкой `name` и получаю parquet с предсказаниями.
5. Как пользователь, на инференсе я получаю уверенный L3 или явный отказ. При этом я могу посмотреть выходы голов L1/L2 и их согласованность с L3, чтобы проверять гипотезы о поведении модели на «чужих» данных.
6. Как пользователь, если во входном parquet инференса есть колонки `L1..L3`, я получаю те же метрики, что и при обучении. Это нужно для проверки на отложенных или новых данных.

## 4. Функциональные требования

### 4.1. Загрузка и проверка данных

**[Р] Порядок операций фиксирован:**

1. Удаление null и пустых значений.
2. Проверка таксономии.
3. Проверка дубликатов.
4. Сэмпл `max_rows`.
5. Отсечение `min_count`.
6. Маппинг.
7. Сплит.

`min_count` применяется после сэмплирования, чтобы сэмпл не опустил класс ниже порога незаметно.

- Чтение parquet и проверка наличия колонок `name`, `L1`, `L2`, `L3`.
- Отбрасываются строки с пустым или null-значением в любой из этих колонок; их число попадает в отчёт.
- **Проверка таксономии.** У каждой L3 ровно один L2, у каждого L2 ровно один L1. При нарушении ноутбук останавливается с понятной ошибкой и списком нарушений. Проверка дешёвая, поэтому делается всегда, хотя данные заранее проверены.
- **Проверка дубликатов.** Считается число повторяющихся `name`, в том числе с разными метками. Если оно ненулевое, в отчёт выводится предупреждение с примерами. Данные не меняются.
- **Ограничение объёма.** Параметр `max_rows` задаёт стратифицированный по L3 сэмпл, если файл больше; `None` означает «брать всё».

### 4.2. Маппинг классов

- Для каждого уровня строится словарь `label ↔ id` с детерминированным порядком (сортировка по строке).
- Таблицы родителей хранятся массивами id: `parent_l2_of_l3` и `parent_l1_of_l2`.
- Маппинг строится **после** фильтрации редких классов (см. 4.3) и сохраняется в артефакт модели. Инференс использует только сохранённый маппинг.

### 4.3. Сплит

- Стратифицированный по L3 сплит train/val/test. Доли в конфиге, по умолчанию 0.8/0.1/0.1. Фиксированный seed.
- **[Г] Редкие классы.** L3 с числом примеров меньше `min_count` (по умолчанию 10) исключаются из обучения и оценки. Их список и объём попадают в отчёт.
- Сплиты сохраняются по содержимому, как parquet с колонками `name`, `L1..L3` (минимум test, желательно все три), чтобы следующие итерации мерились на том же test. Индексы строк для этого не годятся.

### 4.4. Признаки

- **[Р]** Две TF-IDF-ветки, конкатенированные в разреженную матрицу:
  - **char n-gram.** Из строки после `preprocess` удаляются все пробельные символы (`\s`, Unicode). n-граммы считаются по сплошной строке: `analyzer="char"`, диапазон n в конфиге.
  - **word unigram.** Токенизация только по пробельным символам: `str.split()`, без `token_pattern` sklearn. Пунктуация остаётся частью токена, односимвольные токены сохраняются.
- В обеих ветках `lowercase=False`, так как регистр уже обработан в `preprocess`. Ветко-специфичные преобразования (удаление пробелов, токенизатор) — функции уровня модуля, без лямбд: это нужно для сериализации через `joblib`. Они входят в сохраняемый пайплайн, а инференс использует ровно их.
- Параметры каждой ветки в конфиге: `ngram_range`, `min_df`, `max_features`, `sublinear_tf`, `dtype=float32`.
- Векторизаторы обучаются **только на train**. Допускается обучение на подвыборке train (`vectorizer_fit_rows`) ради памяти.
- **Предобработка.** Вход уже предобработан (§2). Хук `preprocess(texts) -> texts` делает только замену null на пустую строку и `lower()`; на чистом входе он идемпотентен. Хук сохраняется вместе с моделью как часть пайплайна. Позже в него подключится внешний пакет предобработки, поэтому никакой другой нормализации в этой итерации нет.
- **Ограничение по памяти.** Признаковая матрица целиком никогда не материализуется в dense. Батч остаётся разреженным до первого слоя модели. Способ реализации (`torch.sparse`, `EmbeddingBag` с весами и т. п.) выбирает исполнитель.

### 4.5. Модель

- **[Р]** MLP с общим «стволом» и тремя линейными головами: L1, L2, L3.
- Конфиг ствола задаётся списком слоёв, например `hidden=[1024, 512]`, `dropout=[0.3, 0.3]`. Длины списков должны совпадать (с проверкой). Также в конфиге: функция активации, опционально нормализация.
- **Лосс.** `w1·CE(L1) + w2·CE(L2) + w3·CE(L3)`, веса голов в конфиге. Головы L1/L2 — вспомогательные (multi-task). Решение по L3 принимается только по голове L3.
- **[Р] Веса классов в CE.** Режим задаётся в конфиге для каждой головы:
  - `none` — по умолчанию;
  - обратная частота в степени `alpha` (`1/freq^alpha`, `alpha` в конфиге), с нормировкой на средний вес 1.
  
  Веса считаются по train и сохраняются в артефакт. В дальнейшем дисбаланс будет закрываться синтетикой и активным обучением, поэтому здесь нужен только механизм, без подбора.
- **Обучение.** Оптимизатор, lr, batch size, число эпох, early stopping по val (метрика в конфиге, по умолчанию macro-F1 по L3), seed.
- Логируются кривые train/val loss и val-метрики по эпохам, они попадают в отчёт.

### 4.6. Отказ от классификации

- **[Р] Отказ — это отказ.** Результат — либо уверенный L3, либо ничего. Отката на L2/L1 нет.
- **Пустые признаки.** Если вектор признаков строки нулевой (пустая строка или все n-граммы и токены вне словаря), отказ безусловный, `reject_reason="empty_features"`. Модель для такой строки не вызывается, либо её выход игнорируется. Число таких строк попадает в отчёт.
- **Базовое правило.** Отказ, если `max softmax(L3) < τ`.
- **Дополнительное правило (переключаемое, по умолчанию выключено).** Отказ при рассогласовании голов: родитель argmax L3 ≠ argmax L2 (и/или аналогично для L1). Флаги рассогласования вычисляются и выводятся **всегда**, независимо от того, участвуют ли они в отказе. Нужно, чтобы проверить гипотезу о поведении модели на «чужих» строках.
- **Выбор τ.** На val строится таблица и кривая «покрытие / accuracy / macro-F1 принятых» по сетке τ. В конфиге задаётся один из режимов:
  - фиксированный `tau` — режим по умолчанию, `tau=0.5`;
  - целевая точность принятых на val, тогда выбирается минимальный τ, при котором она достигается. Точность по τ немонотонна. Если цель недостижима ни при одном τ из сетки, берётся τ с максимальной точностью, а в отчёт и в лог выводится предупреждение с достигнутой точностью.
  
  Выбранный τ сохраняется в артефакт и может быть переопределён в ноутбуке инференса.
- Калибровка вероятностей (temperature scaling и т. п.) в этой итерации не делается. Ограничение явно отмечается в отчёте.

### 4.7. Метрики и отчёт (обучающий ноутбук)

- `classification_report` на test для L1, L2, L3 в двух вариантах:
  - **без отказа**: L1/L2 по собственным головам и отдельно по пути от предсказанного L3;
  - **с отказом**: на принятых примерах, плюс покрытие.
- Отчёты сохраняются в CSV (`output_dict=True`), так как по L3 они длинные. Колонка `support` обязательна. Классы на границе `min_count` дают в val/test по 1–2 примера, их метрики шумные, и это отмечается в отчёте. В ноутбуке печатается сводка: accuracy, macro-F1, weighted-F1 по уровням.
- Графики в ноутбуке:
  - кривые обучения;
  - кривая покрытие/accuracy по τ;
  - распределение F1 по классам L3 в зависимости от частоты класса в train.
- Топ-N пар «истинный L3 → предсказанный L3» по числу ошибок, CSV.
- Доля рассогласований голов на test, отдельно для верных и неверных предсказаний L3. Это первичная проверка гипотезы для отказа.

### 4.8. Сериализация

- Артефакт — каталог, содержащий:
  - веса модели (`state_dict`);
  - конфиг (JSON);
  - векторизаторы (`joblib`);
  - маппинги и таблицы родителей (JSON);
  - τ и правила отказа;
  - метаданные: версии Python/torch/sklearn, seed, дата, размеры выборок, хэш или путь входного файла.
- Функция загрузки восстанавливает пайплайн целиком: предобработка, векторизация, модель, отказ.
- **Требование.** Предсказания до сохранения и после загрузки совпадают на одних и тех же входах. Проверяется тестом.

### 4.9. Ноутбук инференса

- Конфиг-ячейка: путь к артефакту, путь к входному parquet, путь к выходу, batch size, опционально переопределение τ и правил отказа, `top_k`.
- Вход: parquet с колонкой `name`. Остальные колонки пробрасываются в выход без изменений.
- Выходные колонки:
  - `l3_pred` (null при отказе), `l3_prob`, `rejected`, `reject_reason` (`empty_features`, `low_confidence`, `mismatch` или null);
  - `l3_top1_raw` — argmax L3 до отказа;
  - `l2_from_l3`, `l1_from_l3`;
  - `l2_head`, `l2_head_prob`, `l1_head`, `l1_head_prob`;
  - `mismatch_l2`, `mismatch_l1`;
  - опционально top-k L3 с вероятностями.
- Если во входе есть `L1..L3`, считаются метрики как в §4.7. Метки, которых нет в маппинге модели, учитываются отдельной строкой отчёта и не роняют ноутбук.
- Входной parquet читается целиком. Векторизация и прогон модели идут батчами, без материализации всей признаковой матрицы.

## 6. Фикстуры и тесты

### Фикстуры

Источник фикстур — `data/ods_labels.csv`.

**Основная фикстура.** Это ODS, переведённый в parquet, целиком или стратифицированный сэмпл для быстрых тестов. На ней идут сквозные прогоны ноутбуков. Метрики на ODS фиксируются в `STATUS.md` как проверка работоспособности и целевыми не являются. Если в ODS найдутся нарушения уникальности путей или дубликаты, для основной фикстуры они отфильтровываются, а факт фиксируется в `DECISION_LOG.md`.

**Дефектные фикстуры.** Строятся на основе ODS внесением дефектов:

- дубликаты и пустые значения — для страховочных проверок §4.1;
- нарушение уникальности путей таксономии — для проверки остановки с ошибкой;
- строки, дающие пустой вектор признаков;
- вход инференса без `L1..L3` и с неизвестными метками.

Весь набор фикстур строится из ODS одним скриптом-генератором детерминированно, с фиксированным seed.

### Тесты (pytest)

- проверка таксономии;
- проверка дубликатов (предупреждение без изменения данных);
- признаки: удаление пробелов в char-ветке, токенизация по пробелам в word-ветке;
- веса классов в лоссе;
- стратифицированный сплит и исключение редких классов;
- маппинги и таблицы родителей;
- логика отказа, включая `empty_features`, и флагов рассогласования;
- round-trip сериализации с совпадением предсказаний;
- инференс на входе без `L1..L3` и с неизвестными метками.

### Сквозной прогон

Оба ноутбука исполняются end-to-end на фикстуре на CPU (через `nbconvert --execute` или аналог).

## 8. Процессные артефакты

Директория `artefacts/` в корне репозитория. В ней лежат:

- эта спека;
- `STATUS.md`;
- `DECISION_LOG.md`.

Все три файла коммитятся в тот же репозиторий вместе с кодом.

**Спека** исполнителем не редактируется. Любое отступление от неё фиксируется в `DECISION_LOG.md`.

**`STATUS.md`** — текущее состояние работы. Файл перезаписывается при каждом заметном продвижении и в конце сессии. Содержит:

- по каждому пункту DoD (§9): статус `done` / `in progress` / `blocked` / `todo` и одна строка комментария;
- блокеры и вопросы к Сергею, если есть;
- имя ветки с итоговым состоянием;
- как воспроизвести последний зелёный прогон: команды тестов и исполнения ноутбуков.

**`DECISION_LOG.md`** — журнал решений, только дописывается. Запись делается, когда:

- спека оставляет выбор исполнителю (структура кода, способ подачи разреженных батчей, дефолты и т. п.);
- гипотеза [Г] принята или изменена;
- исполнитель отступил от спеки.

Формат записи: номер, дата, раздел спеки, решение, рассмотренные альтернативы, обоснование, как проверить.

**Артефакты модели и выходы прогонов** (веса, векторизаторы, отчёты, фикстуры-parquet) в `artefacts/` не кладутся и не коммитятся: отдельная директория и `.gitignore`. Код генератора фикстур коммитится.

## 9. Definition of Done

1. Обучающий ноутбук на основной фикстуре (ODS) проходит Run All на CPU без ошибок. Он создаёт артефакт модели и отчёт по §4.7.
2. Ноутбук инференса на фикстуре проходит Run All и выдаёт parquet с колонками по §4.9.
3. Все тесты §6 зелёные.
4. Изменение архитектуры MLP (число слоёв, размерности, дропауты) делается только правкой конфиг-ячейки и проверено хотя бы на двух конфигурациях.
5. Ноутбуки соответствуют §5.2: в ячейках нет определений функций и классов, весь пайплайн воспроизводим из Python-скрипта.
6. Код не зависит от сетевого доступа и предобученных весов. Его можно перенести в целевую среду копированием файлов и установкой `requirements.txt` на Python 3.12.
7. `README.md` содержит:
   - как запустить оба ноутбука;
   - описание конфига;
   - структуру артефакта;
   - ориентиры по памяти и времени.
8. `artefacts/STATUS.md` актуален и показывает все пункты DoD в `done`. В `artefacts/DECISION_LOG.md` есть записи по всем решениям из §8, включая каждую гипотезу [Г].
9. **Коммиты и ветки — на усмотрение исполнителя**, без ограничений. Итоговое состояние — в одной ветке, её имя указано в `STATUS.md`.
